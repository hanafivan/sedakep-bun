2. Temuan penting

Database legacy sangat bergantung pada relasi implisit. Hanya enam foreign key tercatat di MySQL, sedangkan dari pola primary key/kolom ID terdeteksi sekitar 86 relasi kandidat. Migrasi wajib memakai mapping eksplisit dan validasi record, bukan hanya mengandalkan FK.
Keputusan simplifikasi schema: approval terkini yang 1:1 dilipat ke tabel request/service. Tabel approval terpisah tidak dibuat kecuali nanti terbukti membutuhkan riwayat approval 1:N.
Strategi penyimpanan dokumen: file baru ditulis langsung ke MinIO. File lama dipindahkan memakai object key deterministik, checksum, dan status migrasi sehingga proses bisa dihentikan lalu dilanjutkan.
  • Password lama masih MD5 pada login legacy; migrasi auth harus mendukung upgrade hash setelah login berhasil.
  • Nama file database sering hanya filename, sementara lokasi folder ditentukan kode PHP. Scanner migrasi harus memakai pasangan tabel/kolom + mapping direktori.
  • File tidak hanya PDF: ada JPG/JPEG, PNG, DOC/DOCX, logo, dan foto.
  • Filesystem legacy jangan dihapus sebelum audit checksum dan periode fallback selesai.

4. ERD database legacy

Diagram berikut dibuat dari 59 tabel/view, 855 kolom, enam FK resmi, dan 86 relasi kandidat yang diinferensikan dari kolom ID. Garis kuning putus-putus adalah relasi inferred dan wajib dikonfirmasi saat mapping target.

ERD sengaja dibuat lebar dan dapat di-scroll horizontal agar nama tabel serta relasi tetap terbaca. Tabel document_objects belum ada di legacy; itu adalah tabel target untuk metadata object MinIO.

4a. ERD target baru — versi sederhana

Desain disederhanakan berdasarkan audit data legacy. Status/approval terkini yang 1:1 dilipat ke tabel pengajuan. Tabel tambahan hanya dipakai untuk relasi 1:N nyata atau kebutuhan lintas domain.

Aturan schema target

  • leave_requests menyimpan status dan snapshot approval atasan 1/2. Tidak ada tabel leave_approvals terpisah untuk approval terkini.
  • employee_services juga menyimpan status dan snapshot approval. service_documents hanya untuk banyak dokumen layanan.
  • dispositions dan assignment_members dipertahankan karena satu surat bisa punya banyak disposisi/anggota.
  • documents wajib ada karena metadata object MinIO berbeda dari data bisnis. document_links dipakai saat satu entity memiliki banyak field file.
  • audit_logs dan migration_items bukan tabel bisnis; keduanya untuk audit dan migrasi resumable.

UNIQUE(source_table, source_column, source_record_id)
UNIQUE(bucket, object_key)
  1. Scan referensi file dari database legacy dan mapping direktori.
  2. Buat identity deterministik berdasarkan tabel, kolom, ID record, dan filename.
  3. Hitung ukuran + SHA-256.
  4. HEAD ke MinIO; skip jika key dan metadata/checksum cocok.
  5. Upload stream jika belum ada atau tidak cocok.
  6. Verifikasi ulang object.
  7. Commit metadata/status database hanya setelah upload terverifikasi.
  8. Ulangi scan untuk menangkap data baru. Writer aplikasi baru langsung dual-write ke MinIO, bukan filesystem legacy.
Migrasi tidak boleh memakai random object key. Key deterministik adalah syarat agar retry tidak membuat duplikasi.

7. Plan implementasi lengkap

Plan implementasi kini disatukan dalam satu dokumen: docs/sedakep-plan.md. Bagian ini memuat ringkasan fase; detail per fase, gate, dan definition of done ada di file tersebut.

7.1 Rangkuman fase

  1. Baseline dan kontrak perilaku — peta modul, role matrix, enum, kebijakan anomali data, fixture engine PHP.
  2. Schema target dan migration database — migration MySQL bernomor, up/down, unique constraint, seed policy.
  3. Adapter runtime — MySQL + MinIO, healthcheck, endpoint file terproteksi.
  4. Pure quota engine — quota-engine.ts tanpa SQL, aturan N/N-1/N-2, parity test lawan PHP.
  5. Read API — daftar/detail permohonan dan endpoint quota read-only, parameterized SQL.
  6. Create dan edit permohonan — validasi server-side, lock user/tahun, exclude current saat edit, upload aman.
  7. Approval dan workflow — approve per level, reject, cancel, idempotent, rebuild saldo saat final.
  8. Projection, rollover, policy, admin — rebuild, SK/policy, override eligibility, Cuti Besar, audit.
  9. Migrasi data database — import request dan approval, deduplicate, discrepancy report.
  10. Migrasi dokumen ke MinIO — object key deterministik, HEAD/checksum, resumable, final scan.
  11. Frontend React — daftar, form, simulasi quota, approval, histori, admin.
  12. Port seluruh modul bisnis — surat tugas (4.331 baris), alibi (4.287), agenda (1.096), disposisi (7.929), pensiun (5.442), izin belajar (7.715), tugas belajar (1.416), gelar (4.355), karpeg (2.767), karis/karsu (3.556), BPJS (4.368), pangkat (11.524), PMK (824), satya lencana (4.945), SKMI/SKPP (767), taspen (3.573), backup (5.357), PDF/QR. Rincian per modul ada di Fase 12 plan.
  13. PDF, QR, dokumen cetak — generator TypeScript, output ke MinIO, akses terproteksi.
  14. Regression, cutover, retirement — regression matrix, cutover berjenjang, fallback legacy read-only.
