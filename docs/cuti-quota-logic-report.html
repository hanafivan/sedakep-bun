Report Logic Cuti dan Perhitungan Kuota

Aplikasi sumber: /Applications/XAMPP/htdocs/sedakep-ptsp-kemenag-sleman
Database: ptsp_sedakep
Fokus: relasi tbl_surat_masuk sebagai permohonan cuti dan sumber transaksi kuota.

1. Kesimpulan eksekutif

Benar: tbl_surat_masuk adalah tabel permohonan cuti. Kuota cuti tahunan secara bisnis dihitung dari permohonan di tabel ini, tetapi hanya setelah dikaitkan ke status approval di tbl_acc. tbl_cuti_quota bukan sumber transaksi utama; ia adalah materialized snapshot/cache per user per tahun, sedangkan histori yang dapat direplay berada di tbl_surat_masuk + tbl_acc.

Engine terbaru tidak sekadar menjumlahkan semua permohonan. Ia:

  1. memilih hanya Cuti Tahunan;
  2. memilih hanya approval final: acc = Diterima, acc_atasan = Diterima, dan acc_atasan2 = Diterima;
  3. mengelompokkan lama cuti berdasarkan tahun YEAR(tgl_mulai);
  4. mengurangi kuota dengan urutan N → N-1 → N-2;
  5. membatasi carry-over N-1 dan N-2 maksimal 6 hari;
  6. menghanguskan sisa N-2 ketika bucket N-2 tersentuh dalam penggunaan;
  7. mengurangi lagi permohonan yang masih proses sebagai reserved saat memeriksa ketersediaan.

4. Alur bisnis lengkap

4.1 Membuat permohonan

  1. Form mewajibkan identitas, jenis, durasi, tanggal, alasan, alamat, telepon, dan pejabat.
  2. Jenis cuti divalidasi menurut NIP: PPPK hanya Tahunan, Sakit, Melahirkan; PNS juga boleh Alasan Penting, Besar, dan Di Luar Tanggungan Negara.
  3. Periode tutup Cuti Tahunan diperiksa. Source saat ini hard-code 21 November 2025–31 Desember 2025 dan hanya memblokir jika tanggal request overlap.
  4. File boleh jpg/png/jpeg/doc/docx/pdf dengan batas legacy kurang dari 2 MB; nama file diberi angka random, lalu disimpan di upload/surat_masuk/.
  5. Untuk Cuti Tahunan, validateQuotaAvailability menjalankan eligibility dan available balance sebelum INSERT.
  6. INSERT ke tbl_surat_masuk. Belum ada mutation kuota pada saat pengajuan.

4.2 Persetujuan

  1. Approval utama admin mengisi atau memperbarui tbl_acc.acc.
  2. Atasan 1 dan atasan 2 memperbarui acc_atasan dan acc_atasan2.
  3. Status resmi untuk quota engine baru ketika ketiganya Diterima.
  4. Snapshot quota di tbl_acc.tahunan_n... dipakai tampilan/fallback lama, tetapi engine terbaru menghitung ulang dari histori permohonan final.
  5. Source code mengandung fungsi mutasi deductQuota, tetapi alur approval yang diperiksa tidak menunjukkan pemanggilan konsisten; karena itu target tidak boleh bergantung pada mutasi event saja. Saldo resmi harus dapat direbuild deterministik dari leave_requests.

4.3 Menampilkan saldo

calculateSisaCutiFromAccHistory → calculateOriginYearQuota → query semua request Cuti Tahunan final → replay per tahun → map menjadi N/N-1/N-2. Tampilan histori memakai replay snapshot berdasarkan tanggal mulai lalu id surat.

4.4 Mengecek ketersediaan

calculateAvailableBalance mengambil official balance lalu mengurangi reserved days dengan cascade N → N-1 → N-2. N-1/N-2 masing-masing dibatasi maksimal 6 pada output UI. Kalau lama request ≤ available, request valid.

5. Algoritma kuota yang harus dipertahankan

Input: user, targetYear, optional requestToExclude

1. Ambil NIP user.
2. Resolve TMT:
   - PNS: YYYYMM dari digit NIP posisi 9–14.
   - PPPK: lookup tbl_pppk_tmt; jika tidak ada, manual validation.
3. Eligible jika masa kerja >= 12 bulan pada tanggal referensi.
4. Ambil request JOIN approval:
   WHERE jenis_cuti = 'Cuti Tahunan'
     AND user = user
     AND approval utama/atasan1/atasan2 semuanya 'Diterima'
     AND optional id_surat != requestToExclude
   GROUP BY YEAR(tgl_mulai), SUM(lama_cuti).
5. Buat origin quota 12 hari untuk setiap tahun eligible.
6. Replay tahun naik:
   penggunaan tahun Y mengurangi quota Y, lalu Y-1, lalu Y-2.
   Jika bucket Y-2 disentuh, sisa bucket itu menjadi 0.
7. UI:
   N = remaining[targetYear]
   N-1 = min(6, remaining[targetYear-1])
   N-2 = 0 jika ada penggunaan pada tahun target-2, selain itu min(6, remaining[targetYear-2]).
8. Reserved:
   request Cuti Tahunan pada target year tanpa approval final,
   dengan approval utama belum ada atau masih berjalan dan tidak ditolak.
9. Available = official pool - reserved, cascade N → N-1 → N-2.
Catatan penting: terdapat beberapa implementasi lama yang tidak sepenuhnya sama: getOrCreateQuota/recalculateQuotaFromHistory memakai snapshot dan kadang hanya mengurangi N; cuti_quota_advanced.php memakai rollover materialized; engine origin-year adalah sumber perilaku terbaru. Saat refactor, tetapkan satu engine canonical dan buat parity test terhadap engine terbaru.

7. Temuan risiko dan bug migrasi

  • Dead function: recalculateQuotaFromHistory() di include/cuti_quota_advanced.php memakai tbl_acc_atasan1 dan tbl_acc_atasan2. Kedua tabel itu tidak ada di database (hanya tercatat tbl_acc), jadi fungsi tersebut pasti gagal query dan tidak boleh disalin apa adanya.
  • Approval snapshot tidak historis: perubahan status lama dapat mengubah hasil replay. Jika histori audit diperlukan, tambahkan approval events; jika tidak, nyatakan bahwa target mempertahankan current-state semantics.
  • Duplikasi transaksi: terverifikasi 6 id_surat memiliki lebih dari satu baris di tbl_acc, dan 4 baris tbl_acc orphan tanpa request. Engine target harus deduplicate per request id dan melaporkan konflik, bukan men-jumlahkan keduanya.
  • Request belum diperiksa: 31 request tidak punya baris tbl_acc sama sekali; ini masuk kategori reserved.
  • Satuan tidak konsisten: Cuti Tahunan memiliki satuan Hari dan Tahun; quota engine menjumlahkan integer lama_cuti. Target perlu menolak/menormalisasi unit selain Hari atau membuat policy eksplisit.
  • Nilai negatif/nol: terverifikasi 8 baris Cuti Tahunan dengan lama_cuti <= 0 (termasuk -1), 5 Cuti Sakit, 1 Cuti Alasan Penting. Validasi target tidak boleh langsung menganggap semua histori valid; tandai data anomali.
  • User non-aktif: dari 1.730 user, 414 berstatus Non Aktif, 1.176 nilai kosong, 140 NULL. Filter keaktifan rollover legacy memakai tiga kondisi yang tidak identik; tetapkan satu definisi aktif di target.
  • Log audit tidak lengkap: tbl_cuti_quota_log hanya berisi 259 baris dengan satu action DEDUCT, padahal kode mendefinisikan ROLLOVER, SK_PRESIDEN_APPLIED, ADMIN_OVERRIDE, CUTI_BESAR, dan INIT. Artinya rollover dan SK Presiden belum pernah tercatat berjalan lewat jalur itu.
  • Projection tidak update: tbl_cuti_quota hanya memiliki 202 baris per tahun 2020–2025 dan 242 baris 2026, padahal user aktif jauh lebih banyak. Projection legacy memang tidak sinkron dengan seluruh user, sehingga tidak layak dipercaya sebagai sumber saldo.
  • Hard-code periode tutup: periode 21 Nov–31 Des 2025 tertulis di include/cuti_tahunan_tutup.php; tidak boleh disalin sebagai aturan permanen.
  • Race condition: dua pengajuan bersamaan bisa sama-sama lolos available check. Target perlu transaction/lock atau reservation atomik.
  • Perbedaan fungsi: materialized quota (getOrCreateQuota, rollover advanced) dan origin replay dapat menghasilkan saldo berbeda. Hanya satu canonical engine boleh dipakai endpoint baru.

9. Acceptance criteria refactor

  1. Untuk dataset legacy yang sama, official balance per user/tahun sama dengan engine origin-year, termasuk exclude current request.
  2. Reserved tidak mengurangi official balance dan hanya memengaruhi available balance.
  3. Request non-Tahunan tidak memengaruhi quota Tahunan.
  4. Approval kurang satu tingkat tidak dihitung resmi.
  5. Ditolak/dibatalkan tidak dihitung resmi maupun reserved.
  6. Carry-over dan N-2 expiry memiliki test boundary.
  7. Concurrent submission tidak dapat oversubscribe quota.
  8. Rebuild quota dapat dijalankan berulang dan hasilnya sama.
  9. Semua lampiran request bermigrasi ke MinIO atau tercatat missing/orphan.
